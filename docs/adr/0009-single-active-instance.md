# ADR 0009：单活实例，数据目录可迁移

- 状态：提议（跨机器的互斥方案待 Phase 1 设计、验证 2 确认服务器可用性）
- 日期：2026-09-23
- 关联：PLAN.md「横切关注点」单活与迁移、Phase 0 验证 2、Phase 7

## 背景

助手可能跑在本机，也可能跑在服务器上；两处同时运行会重复发信、重复提交。

## 决策

- 同一时刻只有一个活跃实例。
- 数据目录里有带心跳的实例锁，同一份数据上的第二个实例拒绝启动。
- 迁移步骤：停止旧实例 → 推送数据仓库并备份数据库 → 在新机器拉取并恢复 → 重新登录 ehall → 启动。

## 后果

- 单写者，和 SQLite 的约束一致（ADR 0002）。
- 代价：不能“本机跑 ehall、服务器跑邮件”这样按能力拆分运行。

Phase 0 审查发现的缺口：本机和服务器各有一份数据目录副本，锁文件互相看不见，挡不住“两台机器同时运行”——而这恰恰是本 ADR 要防的情形。提议在两台机器都能访问的外部资源上加租约，执行器每次对外写之前确认自己持有租约：

- smail 里的专用文件夹（如 `Assistant/Lease`）放一封带实例 id 和到期时间的信，定期续约；复用已有的 IMAP 连接，不需要额外服务；
- 或数据仓库远端的租约文件，`git push` 成功才算拿到租约。

## 放弃的方案

- 多实例协调（分布式锁、主备切换）：单用户场景成本过高。

## 待验证

- 验证 2：服务器能否访问 ehall。不能的话，ehall 能力只在本机启用；如果那时仍想让服务器处理邮件，就与“单活”冲突，需要在 SPEC 中取舍。
- Phase 1：选定租约方案并写测试；Phase 7：迁移演练验证。

## 2026-09-23 验证进展

本机已完成 HTTP 可达性和手动登录验证。尚未提供用于验证的服务器连接目标，
因此服务器是否可用仍未知；保持数据配置中的 `enabled_on = ["local"]`，不据本机结果推断服务器能力。
