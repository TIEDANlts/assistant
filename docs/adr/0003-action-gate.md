# ADR 0003：动作闸门——确认绑定内容哈希，执行幂等，结果未知时转人工

- 状态：已接受（邮件的核实路径待验证 1 确认）
- 日期：2026-09-23
- 关联：PLAN.md「核心模型」、Phase 0 验证 1、Phase 1

## 背景

实验要求“只发送你确认的最终版本”“不重复发送”。模型会改写内容，进程会崩溃，网络会超时，所以这两条必须由代码保证，而不是靠提示词。

## 决策

- 对外写一律走 Action 状态机：提议 → 确认 → 恰好执行一次 → 记录（状态图见 PLAN.md）。
- 确认绑定 `payload_hash`：对规范化 JSON 取 SHA-256。规范化 = 键排序、UTF-8、紧凑分隔符（`,` 与 `:`）、不转义非 ASCII；payload 中不使用浮点数（金额、时间等一律用字符串或整数），避免表示差异。
- 任何修改都生成新的 ActionVersion；已确认的动作回到 `proposed`，旧确认作废。
- 执行器在 `BEGIN IMMEDIATE` 事务里把 `approved` 改为 `executing`，前提是已确认版本的哈希等于当前版本；外部调用完成后在另一个事务里写结果。
- 超时的 `executing` 动作调用适配器的核实方法（邮件 `find_sent`，ehall `find_submission`）：查到记为 `succeeded`，查不到转 `uncertain` 并推送，绝不自动重发。
- 暂停开关打开时，执行器不领取任何动作。

## 后果

- 两条实验要求都有可测试的实现：确认后改内容 → 执行被拒；发送后崩溃 → 不重发。
- 代价：每个 Writer 都必须实现“核实”方法，否则结果未知时只能转人工。

## 放弃的方案

- 用提示词约束“只发确认版本”：无法验证，模型改写或重试时就会失效。

## 待验证

邮件的崩溃恢复依赖腾讯企业邮的行为，由验证 1（`spikes/smail_probe.py --send-self`）确认：

- SMTP 发出的信会不会自动出现在“已发送”，延迟多久；
- Message-ID 是否原样保留；
- `SEARCH HEADER Message-ID` 是否可用。

如果不会自动保存，执行器发送后用 `append_sent` 自己存一份；如果 Message-ID 被改写或 HEADER 搜索不可用，改用自定义头（如 `X-Assistant-Action: <action_key>`）或主题标记定位。结论写回本节。
