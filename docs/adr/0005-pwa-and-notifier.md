# ADR 0005：手机端用 PWA，推送走通知端口

- 状态：提议（默认通道待验证 5 确定）
- 日期：2026-09-23
- 关联：PLAN.md Phase 0 验证 5、Phase 2

## 背景

实验要求在手机上发起任务、查看进度、修改草稿、确认，且不能依赖桌面端开着的对话窗口；要同时覆盖 iOS 和安卓。

## 决策

- 手机端是 FastAPI + Jinja2 + HTMX 的 PWA，添加到主屏幕使用；所有操作（回答问题、编辑草稿、确认或拒绝）都在 PWA 里完成。
- 推送经 Notifier 端口发出。推送内容只有标题、不含个人信息的摘要和卷宗链接，不带邮件正文；点开后进入 PWA 操作。
- 候选通道：飞书或企业微信群机器人、ntfy、Bark（仅 iOS）。默认通道由验证 5 决定；Web Push 作为后续可选项（iOS 需要 16.4 以上且已添加到主屏幕）。

## 后果

- 零安装成本，双平台一致；通道可以随时替换或并用。
- 代价：推送依赖第三方应用在线；安卓后台推送的可靠性取决于具体 App 和系统设置；链接要能在手机上直接打开 PWA（需要 HTTPS 和可达的地址，见 PLAN.md 部署）。

## 放弃的方案

- 原生 App：开发与分发成本高，iOS 还需要开发者账号。
- 备忘录同步：无法绑定内容哈希确认，也无法可靠地触发处理。

## 验证 5 结果（2026-09-23）

`push_probe.py --channel all` 发现飞书、企业微信、ntfy、Bark 均未配置，退出码为 `2`，没有发送测试消息，也没有手机到达、锁屏或链接打开数据。默认通道仍待配置与设备实测后确定。

## 待验证

验证 5（`spikes/push_probe.py`）：两个候选通道在一台 iOS 和一台安卓设备上各收到测试消息；记录到达时延、锁屏显示的内容、点链接能否直接打开。结论写入 `docs/recon/push.md` 与本节。
